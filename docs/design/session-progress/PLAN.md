## 2. 先识别目标，再归类细节

### 聚合流程
1. 明确范围：工作区、目标、观察窗口。扫描元信息与digest只初筛，不读全量历史作为默认。
2. 抽取“谁希望什么结果、怎样算通过”，保留用户/contract原始证据引用。会话不是任务：同会话拆段、跨会话合并，worker归入其实际工作单元。
3. **稳定ID先行**：已有task_id/subtask_id直接映射；没有ID则分配本地opaque ID，不用可改标题当唯一键。
4. 归并优先：同稳定ID+同验收对象才直接合；同contract hash不足以证明同目标（模板可相同）。只有关键词/时间相近的均进候选，不自动销项。不同工作区不自动合，显式跨区目标只做来源关联。
5. 一次只让人确认少量歧义：候选归并、分拆、目标转移。确认记录主控写入原有决策事实源；第一版不建设第二份override台账。
6. 同任务取最新**适用版本且被接受**的证据，保留“之前X→后来Y”纠正；最新自报不能覆盖旧的正式验收，旧验收也不能用于新版本。

### 层级与语义角色
- L1：人关心的结果，如“新设备可靠接续工作”。
- L2：可验收阶段交付，如“恢复已有工作”“完成发布演练”。
- L3：可执行工作单元，如“核对恢复范围”“检查密钥指针”。原始工具调用/模型轮次只作为证据，不自动变成任务。
- `role=outcome/enabler/unknown`按验收目的判断，独立于层级。技术可以在L1成为目标：如“消除OAuth回调漏洞”；“改回调参数”通常只是支撑手段。未知不默认隐藏。
- 同一技术项服务多个目标时，只保留一个canonical任务；其余是引用/依赖，不重复进度计数。

## 3. 关键识别与视觉聚焦

不采用Opus加权积分，也不把“节点最多的最长链”称作关键路径：无工期与资源数据，无法得出进度管理意义的CPM。第一版按可解释优先级排：
1. 用户当前必须决定且影响未通过验收门；
2. 外部/人工等待，或有未满足硬依赖且影响多个未完项；
3. 验收版本不匹配、证据冲突、待归并。
每项写明“为何重要→影响哪个结果→下一步由谁做”。默认最多3条决策、12个当前层节点、4轨；超额以显式计数入口折叠，**未完成数、风险数不因折叠减少**。其余内容仍保持可读对比度，不降到20%透明。

共用焦点：当前父任务+选中任务+筛选。下钻只展开一个分支；兄弟分支压缩为带状态与风险数的出口，不把整棵树铺开。当前层外的依赖用“外部前提N”端口列出原始端点。首版保留面包屑，URL至少保存视图；焦点深链接可后续增加。

## 4. 三种关系绝不混用

`parent_id`只有归属语义；`depends_on`只存证据支持的硬前置；`track`只是推进线排版。时间先后、一起讨论、同一worker都不能自动产生依赖。

DAG折叠跨层边时，合并为端口+数量，并保留全部底层端点；聚合边可能成环，即便叶子DAG无环。遇到环显示“分组依赖相互关联”，展开细层，不为拓扑排序删边。任务硬依赖本身成环则报数据待修，不虚构层次。无依赖数据时显示“依赖未声明”，不能显示“无依赖”。

轨道仅在系列/并行的可表达子图显示真实汇合门；本次合成稿三轨分别为恢复、交付、安全，共同指向接续验收。对于非平面或跨目标复杂依赖，用有端点标题和数量的“另有N前提”入口切DAG；不做6!轨序搜索、不做全局自动换乘规划、不为了漂亮而造站。图例明确同轨相邻不等于硬依赖。

## 5. 状态、进度、证据

|维度|规则|
|---|---|
|工作状态|适配M5六词：待人工/待决定/待外部/在办/已闭环/作废；不回写M5词义|
|等待原因|另列wait_reason=dependency/human/external/decision，依赖等待并不是M5待外部|
|运行态|queued/running/idle/failed来自job或会话，不能自动决定工作已闭环|
|验收|accepted单独保存，绑定criterion+revision+证据；父级验收独立|
|进度|显示直接子项验收数或必过门数，分母注明口径；不对子孙加权，也不拿命令42%当目标42%|
|新鲜度|按任务特性配置提示阈值；状态过久是“需检查”，不是失败；版本变化立即让旧证据不可用于新验收|
|证据|每条绑定origin=human/tool/self-report、适用target_revision、判定主体与source引用；self-report不自动闭环。原有skill来源顺序用于定位，不是自动裁决算法；提交不等于运行通过，用户验收也不能被更晚commit随意推翻|

原型为比较版，四列展示“待决定/在办/待上游/已验收”，不是正式M5状态schema；正式版采用上述维度映射。原型不演示真实证据裁决。

## 6. 同步方法：先事件驱动，再考虑旁观agent

### A. 主控维护总控区（推荐第一版）
唯一事实源仍为项目已有任务/验收系统；M6数据是只读快照，不是第二个权威账本。每当计划拆分、决定变化、阶段验收、风险出现、交接时，主控先登记原有事实源，再重建目标快照与HTML。worker仍只交receipt。

总控区展示三条：当前目标、最近接受的里程碑、当前需决定；附snapshot revision、source cursor、generated_at、coverage。**不用每个工具调用都同步**；阶段边界更新，用户问“刷新进度”可立即补一轮。快照生成失败保留旧版并显示“上次成功时间/本次失败”，不污染原任务状态。

### B. 只读监控agent（二期可选）
按需启动或有界时段运行，不默认常驻。只读取白名单会话与事实源；文件size/mtime筛变更文件，复用extract解压，多帧完整处理后用event id/seq去重。现有digest有截断，不能宣称无损追踪；首版先批处理，尚不需要专建流式解析器。

监控输出“候选变化+引用+置信+建议”，独立输出区域；不写PTC、Supervisor、M5，不自动合并目标或确认完成。主控核对当前revision后接受，旧revision拒绝。单次有会话数/字节/token上限、止损时间、重试上限，读不到标coverage不全；被日志中的指令诱导也不能扩大授权。

### C. 轻插件容器（有持续查看需求才做）
只新增一个只读入口，加载被批准输出目录里的已脱敏快照；文件白名单/真实路径校验/鉴权沿宿主协议，浏览器不接收任意本机路径。需自动刷新才增加确定性mtime轮询，不为每次刷新调用模型。worktable兼容修复另立任务，不包含于本方案。

### 快照最小契约（拟定，不是已实现schema）

```json
{
  "schema_version": "progress-view/v1",
  "revision": 17,
  "generated_at": "2026-11-04T10:00:00+08:00",
  "scope": {"workspace_id": "workspace-demo", "goal_ids": ["goal-demo"]},
  "coverage": {"complete": false, "unread_sources": ["source-demo-2"]},
  "source_cursors": [{"source_id": "source-demo-1", "through_event": "event-demo-21"}],
  "nodes": [{
    "id": "task-demo", "parent_id": "goal-demo", "title": "确认恢复范围",
    "role": "outcome", "work_state": "待决定", "wait_reason": "decision",
    "acceptance": {"accepted": false, "target_revision": "release-demo"},
    "next_action": "选择配置优先或完整插件数据",
    "sources": [{"source_id": "source-demo-1", "event_id": "event-demo-21"}]
  }],
  "depends_on": [],
  "tracks": []

```

目标ID对应同一nodes集合中的根节点，示例省略了该根节点的完整记录。采用一个snapshot整体替换（临时文件完成校验后原子rename），不让JSON和HTML各自发布半个版本；HTML内联snapshot并回显revision。当前版指针最后更新，生成失败继续提供旧版。源cursor仅在适配器确认来源实际提供稳定event/seq时使用；当前extract不保证这些字段。无稳定事件键时用整文件内容哈希筛变更，重读变更文件并按稳定任务ID重算候选，不声称逐事件无损增量；mtime只筛变更文件。验收与冲突留原事实源，snapshot可删后重建，不另加数据库。

## 7. 最小交付边界

**正式一期**：session-summary增加M6入口+按需参考规范+一个确定性renderer+一个HTML模板；一个snapshot JSON输入，先交付B看板+折叠列表与钻取/证据栏。A/C本轮参考稿已交付，正式增强放二期，共用同一契约而不承诺一期生产化全部视图。M3/M5保持不变。总控元数据走原事实源已有event或附件，不在message堆自创可解析标签语法。

预算：入口说明<=30行；详细规范独立文件；零生产依赖；HTML模板目标<=50KB（不含真实输入数据），先支持每屏12节点/4轨，总量超出分组，不为300节点大图优化。不开数据库/向量库，不建设审批/排程/任务创建/模型路由界面，不导入原始聊天到页面。

**本轮已实现的仅是参考稿**：三视图、节点详情、L1/L2/L3、上钻、列表展开、筛选、切换保焦点。已补子树边界依赖计数与定位；未实现真实聚合、任意跨层聚合端口布局、自动关键识别、归并编辑/持久化、monitor或生产renderer；这些是方案而非已可用功能。

## 8. 主控对 Opus 的取舍

|原提议|裁定|理由|
|---|---|---|
|树/依赖/轨道分离、同数据三视图|保留|避免三套状态互相矛盾|
|最长链加权评分称关键任务|删评分，按决定/阻塞/证据风险排序|无工期不叫关键路径；可解释而非伪精确|
|同cwd+同contract即high，关键词+时间为med|收紧为稳定任务ID+同验收对象|模板contract可同、时间连续不代表目标相同|
|六状态直接作为全部UI状态|拆工作状态/等待原因/运行态/验收|待上游不是待外部；进程结束不代表验收|
|HTML导出override后人工追加新台账|延后|第一版决策复用已有事实源，避免第二真相|
|6轨全排列减交叉|删除|复杂度与收益不匹配，受控轨道+明确DAG出口足够|
|非关键内容20%透明|删除|保留可读性；折叠比灰到看不清更好|
|monitor必须先新建无损游标解析器|延后|批处理可先实现；先验证主动更新是否足够|

### Kimi独立挑战后的最终裁定

[挑战原文](<kimi-challenge.md>)由Kimi只读审查后独立撰写，主控验收如下：
- C1/C2/C5/C6：采纳问题，关键路径评分删除；状态拆维度；证据增加origin、target_revision与判定主体，self-report永不自动关闭；归并比Kimi建议更严格，contract相同仍不足以自动合并。
- C3：当前演示的交付线确在gate.deps内，反例不是当前数据的真实缺陷；但无条件按lane汇合确有泛化缺陷，已加真实依赖祖先守卫，并加入“无关支线不汇合”运行回归。
- C4：采纳，已补子树外部上下游计数、端点清单与跳转。原文箭头表述有反向歧义，以端点from→to为准；正式聚合边布局仍待实现。
- C7/C8：采纳分期；正式一期只有B与数据/证据契约，A/C增强二期，monitor按需，暂不建解析器系统。override导出暂不采纳，决定仍进入原有事实源。
- 对主控两项挑战：明确每屏最多4轨；撤回“默认可按解码event/seq去重”的假设，无稳定事件键时先文件哈希筛变更并重算候选。
- 键盘语义：Opus曾建议Enter下钻，但本稿交互规范选择“点击/Enter选中、明确按钮下钻”，为避免误钻而有意修改，三稿一致。运行与视觉验收不能由静态断言替代，本轮已实际运行Chrome。

以上保留意见由主控作最终裁定，不将worker原答等同最终方案。
