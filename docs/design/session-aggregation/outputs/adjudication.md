### 0.1 版本说明与证据边界

- 6astra 主设计、Opus/Kimi 挑战均针对 **v1.0 通用任务登记**；用户补充后，主控按 Focus Hub 的对象/洞察/阶段/执行门证据收敛为 **v1.1（洞察任务 + Focus Hub 对齐）**。
- 因此：两份挑战对“摄取/身份/证据/评估/运维”的结论继续适用；**洞察专项**（摘要 vs 洞察、洞察去重、新颖性、执行门、改进闭环）由主控在 §4.1 补充挑战与裁决。没有让模型对未读过的 v1.1 冒充已评审。

### 0.2 用户裁决（2026-11-13）

- **D1 已确认：模式 B**（飞书原话「模式b」）。已写回设计第十三节与自检卡：已映射任务只读上游；未映射任务有登记权威（非执行/验收）；不写回。
- 用户追问「focushub 和本项目能否合并？」。主控结论：**能合并，按“同一产品、两个组件”合并**（Focus Hub 工作台/对象权威 + 本项目摄取/提炼适配器），不立刻做单进程/单存储合并；详见设计 15.7.1，决策项 D17/D21。此结论是基于 Focus Hub 现有对象模型/单进程边界与实测盘点的建议，不是已实施。

### 0.3 Focus Hub 实现核对（2026-11-13，v1.2）

- 用户要求「深度理解 focushub 既有设计和已实现内容，更新一个方案」。主控只读核对 Focus Hub 代码/文档/数据，并跑 `325` 模块 + `19` 服务端测试（全过）。
- 核对结论：**Focus Hub 不是只有设计**。已有 DSH 多帧扫描（`dsh-source`）、flow-runner、V1 分析适配器、对象库/API、建议收件箱、任务树/项目/阶段/验收、状态映射；当前 216 活跃对象/28 SESSION（均有 cursors）/95 创建/17 活跃洞察/16 任务/6 项目。
- **V2 洞察未实现**：现有分析只到 V1（summary/insight/suggest-task/artifact），类型/边界/新颖性/去重/提升闭环仍是设计/离线评测。
- **P0 新发现（2026-11-13）**：`dsh-source.firstFrameText` 对 >1MiB 文件只取 1MiB 解首帧；1,384 个 v4 文件中 191 个 ≥1MiB，191/191 失败；完整 buffer 可正常解。**这是复用前的阻断项，不是测试覆盖到的能力。**
- 因此 v1.2 裁决：**D22 先修 `firstFrameText` 1MiB 再复用** DSH/对象/分析，不重写；**D23 V2 元数据先增量写 `derived_from`**；**D24 全局摄取独立 cursor**；先做文本-only，工具/todo 后置。
- 核对证据：[focus-hub-audit.md](focus-hub-audit.md)；设计第十六节；数据/测试日期 2026-11-13。

## 2. Opus 5 挑战裁决

| ID | 挑战摘要 | 严重度 | 裁决 | 设计改动 | 理由 |
|---|---|---|---|---|---|
| O-C1 | 任务/段/证据三层处理不了“Claude 定义、Cursor 实现、Codex 测试”的跨 Agent 分工 | 高 | 采纳 | 5.9 加 `provisional_anchor`、`cross_session_anchor`、`evidence_refs[]`（带 provider_session/role）；P1 只人工 link | 硬锚点跨源天然稀缺；先建临时锚再收证据，避免强行合并 |
| O-C2 | 同名仓库/路径被当强锚点，误合并 | 高 | 采纳 | 4.1 加 `canonical_path + repo_id + 提交范围`；同名目录不单独作锚点；规范化失败降级候选 | 本机确有同名目录/worktree；路径不等于身份 |
| O-C3 | Cursor 标 partial 会掩盖 IDE 覆盖缺口 | 中 | 采纳 | 4.2/13 D8：Cursor transcript-only；IDE 标 `unsupported`；任务带 `coverage_uncertainty` | partial 容易被理解为“已尽力”，必须显式说缺什么 |
| O-C4 | 无验收标准时模型推导“隐含验收”，自动进待验收 | 高 | 采纳 | 6.3 明确：验收标准只能由授权人显式定义；`acceptance_undefined`；队列积压 >10 条/4h 降级候选 | 验收是防伪完成的核心；模型推导等于自证 |
| O-C5 | “只读投影”与“未映射任务的登记权威”矛盾，会变成第二任务系统 | 高 | 采纳 | 10 明确模式 B：已映射任务只读上游；未映射任务有登记权威（非执行/验收）；`task_provenance` 静态 | 责任必须二分，不能混 A/B/C |
| O-C6 | 账本与投影缺同步点，崩溃后可能重复/错序 | 中 | 采纳 | 7.2 加 `projection_checkpoint`；批次 fsync + 投影 COMMIT；只从 checkpoint 后重放；`integrity-check` | 追加日志与投影必须有可恢复的提交单位 |
| O-C7 | OpenCode `time_updated` 非单调导致漏读 | 中 | 采纳 | 4.4 改复合水位 `(id, time_updated)`；`time_skew_detected` 进入审计模式，暂停增量 | 单时间戳水位在并发/回拨下不成立 |
| O-C8 | 源删除/轮转后证据无法复核 | 中 | 采纳 | 9 加 `digest_snapshot` + 脱敏短摘录；源消失标“证据已失效”；Cursor 加密根 blob 标 unsupported | 回链不能只靠路径；要有可对账的采集时摘要 |
| O-C9 | 摘要/段落里可能混入凭据，模型“看过”就无法保证忘记 | 中 | 采纳 | 9 加：凭据在摘录生成前过滤；高熵串删除；模型输出再扫描；失败则 `processing_filtered` 不进模型 | 源头不发送是主防线，不能靠“模型会忘记” |
| O-C10 | 单源故障导致投影字段缺失但无信号 | 中 | 采纳 | 8.4 加 `source_health`、缺失清单、恢复对账 | “没读到”不能显示成“没有” |

**Opus 建议的 MVP 删减与裁决**

| 建议 | 裁决 | 说明 |
|---|---|---|
| 删掉跨源自动关联与模型补盲 | 采纳 | P1 只做单源 DSH + 人工 link；P2 才做跨源提议；自动关联始终只对 A0/A1 |
| 删掉 Cursor 支持与完整性承诺 | 采纳 | P1/P2 标 `unsupported`；P3 仅 transcript partial；解密失败就永久 unsupported |
| 删掉自动状态推进与隐含验收条件推导 | 采纳 | 无显式验收标准不推进；自动推进只走 6.3 白名单 |

**Opus 指出的未回答问题与裁决**

1. **同一 PR 多来源记录如何权威**：采纳问题。按字段分权威：PR 状态以 GitHub 为准，会话引用只作证据；Codex 的本地 PR 数据标 `advisory`；冲突不合并，显示来源。
2. **投影/日志不一致如何检测**：采纳。`projection_checkpoint` + `integrity-check` 命令；输出“日志最后 seq / 投影最后 seq / 差异数”。
3. **权威冲突如何让用户快速裁决**：采纳。CLI/DSH 提供 `authority set <task> <field> <system>`；写入 `authority_decision`；没有决定时显示冲突，不静默选边。

**Opus 对主控约束的反挑战与裁决**

- **“3/5 计数”是否伪精确**：采纳澄清。输出“已验收目标：A、B、C（3 条，未加权，未含依赖）”，不输出比例；分母/口径必须写明。
- **跨 Agent 事实无法回链单一会话**：采纳。`evidence_refs[]` 允许数组，每项带 provider_session；事实可拆分为子事实，展示时保留“同一用户行为”的分组。
- **“进入上游”的定义**：采纳。用静态 `task_provenance=upstream:<system>:<id>` 或 `registry-only`；不允许动态切换；新增来源只建 alias/关系。



## 3. Kimi K3 挑战裁决

| ID | 挑战摘要 | 严重度 | 裁决 | 设计改动 | 理由 |
|---|---|---|---|---|---|
| K-C1 | 首建回填与日预算矛盾，首日产生 1,000+ 审查队列 | 高 | 采纳 | 5.7 加“回填不进默认队列”；`review_items.origin=backfill|incremental`；队列上限 200，溢出降级 related；任务卡标 provisional | 首日体验决定存亡；回填不应把确认成本一次性摊给用户 |
| K-C2 | DSH 多帧 zstd 依赖未声明；只解首帧会静默 partial | 高 | 采纳 | 4.2 加“记录数=1 且文件>10KB 硬告警”；事件 ID 含 generation；14 加帧迭代 spike；依赖清单写明 zstd CLI/帧迭代器 | 已实测 Node 只解首帧；静默漏读比报错更危险 |
| K-C3 | OpenCode 1.9GB 活库读取顶 WAL、拖慢写入方 | 高 | 采纳（首建备份后置 P2） | 4.2 改 `mode=ro`+`PRAGMA query_only`+15s 限时；首建用在线 backup API 到临时副本；WAL 大小进 lag；不复制裸主库 | 只读短事务不保证不阻塞；WAL 是共享资源 |
| K-C4 | OpenCode/JSONL/DSH 水位在时钟回拨、重写、compaction 下漏读 | 中 | 采纳 | 4.4 加各源注入测试；JSONL offset 首行校验；DSH 记录“重扫次数/周”指标 | 水位正确性必须可测，不能靠“重叠窗口”安慰 |
| K-C5 | Windows 运维假设过轻（未登录计划任务、锁残留、长路径、端口、UTF-8） | 中 | 采纳 | 3.3 加 named mutex、登录触发、`\\?\`、named pipe、UTF-8；8.1 加崩溃后锁自愈验收 | 本机就是 Windows，这些会真实发生 |
| K-C6 | 成本“便宜”缺首建实测，止损阈值过粗 | 中 | 采纳 | 8.1/8.2 加“先采样 50 会话再定预算”；连续 3 天超限自动切规则-only | 预算应来自实测，不是拍脑袋 |
| K-C7 | 隐私默认呈现误导：模型跑在哪、凭据漏检、“已脱敏”暗示 | 中 | 采纳 | 9 加模型位置前置裁决；UI 文案改“已检测，非保证”；审计不存 digest；FTS 只索引获准摘要 | 默认设置比技术能力更影响信任 |
| K-C8 | 200 段/50 任务撑不住 98%/80% 门槛，且无对抗集 | 高 | 采纳 | 2.3 加锚点覆盖率；11 加时间切分、100 对硬负例；报告加队列负担、回放差异、证据可定位率 | 统计上 200 次零错误仅贴线；需要负例 |
| K-C9 | 源删除后证据断链；解析器版本混布；quarantine 静默 | 中 | 采纳 | 8.4 加 `source_available=false`、解析器升级显式重解析、quarantine 计数进仪表盘 | 源被清理是常态，不是异常 |
| K-C10 | 登记表是第五个孤立视图，review 队列发散后用户放弃 | 高 | 采纳 | 11 加“taskboard/dashboard 至少一处展示登记投影”；8.1 队列上限；P1 先嵌入既有入口 | 工具必须嵌入现有动线，而不是新增一个入口 |

**Kimi 建议的 MVP 删减与裁决**

| 建议 | 裁决 | 说明 |
|---|---|---|
| 删掉自动关联评分/置信带 | 部分采纳 | P1 只保留 A0/A1 硬锚点自动；0.75–0.98 置信带推迟到 P2，且受队列上限约束 |
| 删掉 Codex/Claude/OpenCode/Cursor 四个适配器 | 采纳 | P1 只做 DSH；P2 接 Codex/Claude；P3 接 Cursor/OpenCode。用户要求的多源支持保留在路线图，不塞进 MVP |
| 七类卡只保留 goals/artifacts/todos | 部分采纳 | 七节**都要渲染**（用户明确要求），但 P1 只自动填 goals/artifacts/todos；方案/裁决/洞察/总体计划显示“未提取/人工填写”，P2 再自动补全，禁止模型硬编 |

**Kimi 指出的未回答问题与裁决**

1. **task_id 跨重建/换机稳定性**：采纳。ULID + 重定向表 + 导出/导入；外部引用旧 ID 时保留 alias；P0 验收加“导出/导入后旧 ID 可重定向”。
2. **OpenCode todo 无独立 id**：采纳。去重键 `(session_id, position, content_hash)`；内容编辑视为新版本，不覆盖旧 todo。
3. **模型运行位置与 5 分钟 SLA**：采纳。证据层 5–15 分钟；任务层异步；模型位置列为 D14 前置裁决，不假设本机 GPU。

**Kimi 对主控约束的反挑战与裁决**

- **锚点覆盖率**：采纳。2.3 要求同时报告有硬锚点段占比；精确率只在有锚点子集上解释，避免“达标但没用”。
- **源删除后的证据回链**：采纳。入库时必须可回链；来源消失后保留事实并标“证据已失效”，不静默隐藏；绝对化的“无来源不得入库”改为“入库时必须有来源，失效后显式标记”。

## 4. 采纳后的设计改动清单

已落入 `design-v1.0.md`（v1.1 内容）：

1. **第〇节需求收敛**：主对象从“任务卡”改为 Focus Hub 式对象（SESSION/INSIGHT/TASK SUGGESTION/TASK/MILESTONE/ARTIFACT/DECISION/RULE）；五个能力=聚合/追踪/去重/洞察/提升。
2. **第十五节洞察模型**：洞察 schema、任务建议、阶段/轨道/里程碑、任务与洞察分开去重、提升闭环、Focus Hub 方案 A 集成。
3. **P1 收窄为 DSH-only**；P2 接 Codex/Claude + LLM 提炼；P3 接 Cursor/OpenCode + 提升闭环；P4 才考虑写回。
4. **只保留 A0/A1 自动关联**；A2 人工；回填不进默认队列，队列上限 200。
5. **事件 ID 含 generation**；DSH 多帧 zstd 硬告警；OpenCode 只读/限时/在线备份；JSONL offset 校验。
6. **Windows 运维清单**：named mutex、登录触发、长路径、named pipe、UTF-8。
7. **证据失效**：`source_available=false`；删除/墓碑/审计；解析器升级显式重解析。
8. **隐私**：模型位置前置裁决；“已检测，非保证”；审计不存 digest；FTS 只索引获准摘要。
9. **评估**：时间切分、100 对硬负例、锚点覆盖率、队列负担、回放差异、证据可定位率。
10. **七节都渲染**，但 P1 只自动填目标/成果物/待办；方案/裁决/洞察/总体计划人工或空。
11. **Focus Hub 集成**：聚合器只提交 Focus Hub 兼容对象；不直接改 `objects.jsonl`；阶段推进/验收仍由人工/Focus Hub 权威完成。

## 4.1 洞察专项挑战（主控补，因模型挑战基于 v1.0）

| ID | 挑战 | 严重度 | 裁决 | 设计处置 |
|---|---|---|---|---|
| I1 | 把“摘要换词”当洞察，卡片很多但无新认识 | 高 | 采纳 | 洞察必须有 `why_keep + scope/boundary + nature`；与 summary 分 `subkind`；无新认识的候选可保留为摘要，不强制升洞察 |
| I2 | 用文字相似度合并洞察，把相反观点吃掉 | 高 | 采纳 | 去重键 `claim + conditions + outcome`；相反观点并列 + `contradicts`；人工拒绝生成 `do_not_merge` |
| I3 | 没有先验快照却宣称“新洞察” | 中高 | 采纳 | 每个提炼批次带冻结先验快照；无快照则 `novelty=unknown`，不写“首次/全新” |
| I4 | 任务建议直接变成任务，重复建顶层任务 | 高 | 采纳 | 建议不是任务；先匹配已有任务；只有用户采纳才建；建任务需带完成标准/未知项 |
| I5 | 洞察被采纳 = 可用于改任务/规则 | 高 | 采纳 | 两道门：阅读/引用门默认开；执行门（改任务/规则/行为）必须确认并记录主体/时间/revision |
| I6 | 阶段由模型/关键词直接判定，误报“验收” | 中高 | 采纳 | 阶段由证据识别 + `stageBasis`；人工纠正优先；`accepted` 只由人工/上游验收记录产生 |
| I7 | 改进没有实测就写成成功/SOP | 中高 | 采纳 | 改进必须有验证方式与结果；无实测标 `unverified_improvement`；一次成功只算参考案例，不升级通用 SOP |
| I8 | 直接写 Focus Hub `objects.jsonl` 绕过 API，破坏版本/执行门 | 高 | 采纳 | 只经 Focus Hub API/outbox 提交；不直接改运行数据；写入幂等、可回滚、留审计 |
| I9 | 跨 Agent 同一洞察重复成多张卡，证据分散 | 中 | 采纳 | 同一主张/条件/结果合并证据，保留多来源；条件不同则相关不合并；重复率进仪表盘 |
| I10 | 洞察/建议太多，阅读负担压垮用户 | 中高 | 采纳 | 按“价值 + 相关性 + 新近”排序；每屏上限；低价值折叠不删除；用户偏好反馈进入排序，但不自动丢原始材料 |

## 5. 未采纳的挑战与理由

| 挑战 | 未采纳/降级的理由 |
|---|---|
| “七类卡只保留 goals/artifacts/todos”（Kimi） | 部分采纳。用户明确要求七节；全部渲染，但 P1 只自动填三节，其余人工/空，避免模型硬编。 |
| “只做 DSH，永远不接其他源”（Kimi 的 MVP 建议） | 部分采纳。P1 只做 DSH；多源是用户明确目标，保留在 P2/P3，不塞进 MVP。 |
| 6astra “60 秒增量、5 分钟发现” | 未照搬。默认 5 分钟发现/60 秒增量可配；Windows 单机资源有限，先以可调参数落地，P1 实测后再定。 |
| 6astra “注册表放 `~/.local/share`” | 改为 `%USERPROFILE%\.dsh\session-registry`，与 DSH 备份/权限模型一致；可配置。 |
| 6astra “43–59 人日” | 采纳为全量估算；v1.2 复用 Focus Hub 后 MVP P0+P1 约 11–17 人日，避免用全量数字吓退第一阶段。 |
| “用标题/语义相似度自动合并”（如出现） | 拒绝。只在 A0/A1 硬锚点自动；A2/A3/A4 人工。 |
| “PR merged 即任务 done” | 拒绝。PR merged 只到 `in_review`/`verified`；done 需人工或上游权威。 |
