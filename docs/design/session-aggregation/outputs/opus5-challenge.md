# Opus 5 独立挑战：多 Agent 会话聚合与统一任务登记

## 结论（≤150 字）

设计在身份模型、合并规则、权威边界三处存在结构性缺陷，会导致实际运行中数据污染而非聚合。任务/段/证据三层不足以处理"同一任务在多 Agent 各做一半"的常见场景；合并规则被同名不同项目、跨 Agent 重复劳动击穿；与存量系统的边界自相矛盾——声称"只读投影"却又声称"未进入上游的登记权威"，事实上会演变为第二套任务系统。首期应从 MVP 删掉跨源自动关联、模型补盲和 Cursor，专注 DSH 单源的证据流水线。

---

## 挑战清单（C1–C10）

### C1：身份模型无法处理"同任务跨 Agent 分工"

**严重度：高**

**主张**：任务/段/证据三层模型假设每个 Agent 会话内的任务是连贯的。当用户在 Claude 定义目标、在 Cursor 实现、在 Codex 测试时，三层模型会将其识别为三个独立任务或强行错误合并。

**反例**：
- Claude 会话 session_claude_001 中，用户提出"优化导出性能"（目标已确认）
- 用户在 Cursor 会话中开始编码实现，生成 PR draft，没有重述目标
- 用户在 Codex 会话中运行性能测试，得出"降低 40%"报告
- 三个会话的"分段/锚点"各自独立；目标、方案、成果物分散在三个来源
- 当前模型靠强锚点（PR、commit、测试输出）匹配，但 PR draft 可能没有链接到 Claude 定义的任务 ID；测试输出可能只有命令名，没有跨源追溯

**最小修正**：
1. 引入"跨源任务快照"机制：用户或模型提议将 Claude 定义导出为临时 task_id（带来源引用），发送给 Cursor 和 Codex 用作 anchor
2. 在段的统一事件模型中加 `cross_session_anchor` 字段，允许显式记录"此段属于 task_id，证据引自会话 X"
3. 证据的 `evidence_ref` 需包含"提供者会话"，不只是"来源类型"

**一期还是后置**：一期必须设计（不必实现），否则早期数据会被误分类。但自动跨源关联推后；先允许用户在 CLI 手工指定。

---

### C2：合并规则被"同名不同项目"击穿

**严重度：高**

**主张**：置信度阈值 0.98 + 强锚点的设计，依赖项目、仓库等路径锚点。但 DSH、Codex、Cursor、Claude 各自记录 cwd、仓库信息的格式和精度不同；重名仓库、worktree、本地副本会造成假阳性合并。

**反例**：
- 本机有 `~/work/repo-a` 和 `~/backup/repo-a`（同名，不同改动）
- DSH 会话记录 cwd 为 `~/work/repo-a`；Cursor 会话（可能因 worktree 切换）记录为相对路径或符号链接
- 模型提取的"项目身份"都是 `repo-a`，强锚点规则认为两个会话讨论同一仓库
- 目标、PR、commit 都不同，但因同名仓库被认为是同一任务的不同进度，自动合并
- 验收时发现成果物不一致，但修正已被记录为"冲突"，而非"误合并"

**最小修正**：
1. 路径规范化必须在适配器层完成：`parse()` 返回规范化后的绝对路径 + inode/dev（如可得）
2. 强锚点规则改为"同名仓库 AND 相同提交范围"，而非"同名仓库"单独作锚点
3. 若路径规范化失败，降级为候选，不进自动关联

**一期还是后置**：一期。第 0 阶段 spike 必须包含路径规范化与身份验证。

---

### C3：Cursor partial 支持掩盖覆盖缺口

**严重度：中**

**主张**：设计规定 Cursor 首期仅接入可解析 CLI 转录，标记 capability 为 partial，文案说"其他路径未验证"。但实现中，未验证的路径会被默认忽视而非显式报告；用户会认为"Cursor 数据都在了"。

**反例**：
- 用户在 Cursor IDE（图形界面，无 CLI 转录）中进行了关键重构，生成 5 个 PR、修改 10 个文件
- 登记表展示"Cursor 数据来源：114 条转录"，但这些 PR、修改都不在其中
- 任务的"成果物"字段显示 partial coverage，但用户会把 partial 理解为"已尽力"，不会意识到关键工作被漏掉
- 后续在 taskboard 中看到重复标题时，未意识到上游 Cursor 数据缺失，导致任务被误判为"已完成"

**最小修正**：
1. 覆盖诊断必须在展示层强制输出：`Cursor 数据覆盖: 114/? (IDE路径未验证，可能漏失 50%+)`
2. Cursor 作为来源的任何任务必须带标志 `coverage_uncertainty=true`，在完成判定时予以保留
3. 第一期不接入 Cursor IDE，仅标记为 unsupported，不标 partial

**一期还是后置**：一期改规则。Cursor IDE 完整支持后置。

---

### C4：状态自动推进被"报告完成"击穿

**严重度：高**

**主张**：设计说"todo=completed、job=settled、助手'已完成'只记作报告"，且"只有已定义验收条件全部具备对应证据时才可进入待验收"。但在实际运行中，当一个任务缺乏显式验收条件时（很常见），模型会从会话内容推导"隐含验收条件"（如"输出文件存在"），进而生成证据列表，人工审查队列一忙就积压，operator 被迫接受自动推进。

**反例**：
- 任务"修复导出重复行"无显式验收条件定义
- 助手完成代码、输出"已完成，CSV 无重复行"
- 模型推导验收条件：[文件路径存在、测试输出包含"passed"]
- 相应证据已被记录：[commit hash、test log file reference]
- 系统自动进入待验收状态
- 人工审查被打断，两小时后无人确认；自动推进至已验收
- 一周后用户发现生产环境有其他边界场景的重复；追溯发现根本没有端到端测试

**最小修正**：
1. 验收条件必须由授权人（非模型）显式定义，不能推导
2. 若缺乏验收条件，即使有"报告证据"也停留在"进行中"，并在展示中标记"待定义验收"
3. 人工确认队列积压 >10 条且 >4 小时，自动降级新的自动推进为候选，不自动进待验收

**一期还是后置**：一期规则（强制代码实现）。

---

### C5：与存量系统的边界自相矛盾

**严重度：高**

**主张**：十章说"登记表是跨源只读投影，仅对自身的关联、来源记录及人工纠正日志负责""未映射到存量系统的任务是'未登记候选'，不是第二套正式任务"。但同时说"确认任务存在后…可由明确工作证据…推进状态"和"自动推进边界"，这意味着登记表在所有权上进行了决定，而非仅读。

**反例**：
- taskboard 中有任务 "T001: 修复导出"，状态为"进行中"
- DSH 中有会话证据记录"用户完成实现、测试通过"
- 登记表自动将此任务从"进行中"推进到"待验收"
- taskboard 中原任务仍为"进行中"（权威未更新）
- 用户查看 taskboard，看到"进行中"；查看登记表，看到"待验收"
- 运维需要查证"这个任务到底什么状态"时，无统一答案
- 若后续要写回 taskboard，发现登记表已做的推进与 taskboard 的权威规则不兼容，需要回滚

**最小修正**：
1. 明确定义三种映射模式，**选择一种**：
   - **模式 A（纯只读）**：登记表只展示来源事实及已有权威状态，不做任何状态推进；用户或权威系统决定
   - **模式 B（投影权威）**：登记表对"未映射任务"有完整权威，对"已映射任务"只读权威状态，不修改；需显式区分
   - **模式 C（受控写回）**：登记表可推进状态，但先在 outbox 中待权威读取确认，后续再做反向同步；需幂等接口支持
2. 当前设计混合了 A 和 B/C，导致责任不清
3. 第一期采纳模式 A，三个月后再评估 B 或 C 的可行性

**一期还是后置**：一期裁决（从十三章"裁决候选"明确选择）。

### C6：并发写与投影一致性缺乏同步点

**严重度：中**

**主张**：设计说日志是 append-only JSONL，SQLite 是可重建投影，崩溃时从日志补齐。但未定义"日志已落盘与投影已同步"的同步点；并发读任务表时，可能看到投影已更新但日志尾批次未提交，或反向情况。

**反例**：
- 事件日志 `.jsonl` 累积 100 条，未刷盘
- SQLite 投影已执行 `COMMIT`，包含前 98 条
- 进程崩溃
- 重启时，从日志补齐：读到第 100 条，认为投影缺第 99、100 条
- 向投影中追加第 99、100 条；但投影中的第 98 条与新追加的第 99 条关系外键冲突（因为第 98 条的 revision 指向已合并的第 99 条）
- 投影重建失败，需要人工恢复

**最小修正**：
1. 定义明确的提交单位：日志批次刷盘 + 投影 `COMMIT` 要么都成功，要么都失败
2. 引入 `projection_checkpoint` 表，记录"已投影到事件日志的最后 seq"
3. 重启时，只从 `checkpoint` 之后的日志行追加到投影，不重放已投影行
4. 日志与投影必须同步刷盘，或使用 WAL 模式下的 fsync 保证

**一期还是后置**：一期架构决定（实现时优先）。

### C7：OpenCode 并发写与水位推进不可靠

**严重度：中**

**主张**：设计说"按各表 `time_updated` 加稳定主键复合水位推进"。但 OpenCode SQLite + WAL 中，若同一表的多行并发更新，`time_updated` 可能不单调；设计提到"若时间不单调，需分区审计补漏"，但未给出补漏的具体规则，只说"分区"。

**反例**：
- OpenCode 消息表，`time_updated` 字段由服务器生成
- 两个客户端并发写入消息，时间戳分别为 `10:00:00.001` 和 `10:00:00.000`（后者晚到但时戳更早）
- 登记服务按 `time_updated` 作为水位，设为 `10:00:00.001`
- 下次增量读取从 `10:00:00.001` 之后，漏掉了 `10:00:00.000` 的消息

**最小修正**：
1. 放弃单一 `time_updated` 作水位；改用`(主键, time_updated)` 复合水位，且记录 read_snapshot_xid（SQLite 快照隔离）
2. 每批查询使用 `BEGIN IMMEDIATE TRANSACTION`，获得当前行级一致性
3. 若时间戳不单调，不重试，改为报告 `time_skew_detected`，暂停增量，进入"审计模式"（逐行对比旧投影）
4. 审计完成后再恢复增量

**一期还是后置**：一期设计决定；第 2 阶段实现。

### C8：证据回链不保证数据找得回来

**严重度：中**

**主张**：设计说"证据必须可回链"，`evidence_ref` 包含路径、行主键、字段路径。但对于压缩、删除、轮转的文件（DSH 的 zstd、Codex 的归档），即使有 reference，也不保证源文件还存在。设计提到"不记录或外发 `blobEncryptionKey`"，但也没说加密的根 blob 无法解密时怎么办。

**反例**：
- 事实记录："DSH 会话 session_001 第 12 条消息包含'完成工作'"
- `evidence_ref: {source: dsh, resource_id: session_001, record_ordinal: 12}`
- 三个月后，session_001 的原始 zstd 文件被用户删除或被 DSH 自动轮转到归档
- 用户要求复核"这条事实真的存在吗"，但已无法解压验证
- Cursor 根 blob 加密，密钥不持久化，无法在三个月后重新解密叶子消息

**最小修正**：
1. 对高风险源（压缩、加密、有删除策略的），必须在采集时同步持久化"脱敏但可验证的内容摘录"
2. `evidence_ref` 包含 `digest_snapshot` 字段，记录采集时刻的内容 hash，即使源不可得也能对账
3. 脱敏摘录保留期限明确写入，例如"90 天自动清理"
4. Cursor 加密根 blob：首期标记为 unsupported，不尝试采集

**一期还是后置**：一期规则；Cursor 完全支持后置到第 3 阶段。

### C9：模型"无工具权限"与隐私检测的覆盖缺口

**严重度：中**

**主张**：设计说"模型无工具权限，输出经 schema、证据存在性、权限门禁三重验证"，且"凭据检测先于模型"。但送给模型的文本已经是会话摘录或段落，凭据可能已经混入摘要；信息论上，若摘要包含部分凭据，模型就看到过，而不只是"检测后替换"。

**反例**：
- 会话文本：用户说"我用 token abc123xyz 连接生产库，执行查询…"
- 凭据检测替换为 `[REDACTED_TOKEN]`
- 模型接收"`我用 [REDACTED_TOKEN] 连接生产库，执行查询…`"
- 模型虽看不到 abc123xyz，但知道"有一个 token 被用于连接生产库"
- 若后续两个不同会话都有类似 pattern，模型可能推导出"这两个 [REDACTED_TOKEN] 是同一个"（基于上下文相似），进而在关联时产生关于凭据的元数据推论
- 这个元数据被记入投影，后续可能被导出或用于模型训练

**最小修正**：
1. 凭据检测必须在"摘录生成"之前；即解析器层面就要去除，不是在模型输入级别
2. 模型输入必须经过"摘录黑名单"验证，不仅替换已知凭据格式，还要删除高熵段落（例如 base64 串、16 进制串超过阈值）
3. 模型输出中的"[REDACTED_*]"计数和分布必须与输入一致，否则拒收（模型可能试图逆向推断）
4. 隐私检测失败时，该文本段不进模型，改为标记 `processing_filtered`，保留索引但不生成派生内容

**一期还是后置**：一期规则（实现后置）。

### C10：单来源故障导致投影不一致且无清晰失败信号

**严重度：中**

**主张**：设计说"单来源设置超时、内存额度、隔离队列与熔断，坏文件不阻塞其他来源"。但投影中来自多个来源的外键关系会被部分来源故障破坏；例如任务 T001 由 DSH 和 Codex 共同关联，DSH 源读失败，则关联不完整，但投影不会显示"因 DSH 故障关联不完整"。

**反例**：
- 任务 T001 的"方案"来自 DSH，"成果物"来自 Codex
- Codex 归档文件损坏，读取失败
- 系统记录"Codex 故障，跳过该批"
- 投影中任务 T001 的方案字段存在，成果物字段为空
- 用户看到成果物为空，以为"还没有成果"，而非"数据读取失败"
- 用户在 taskboard 中手工补充成果物，后来 Codex 恢复了，自动补齐成果物，两个版本冲突

**最小修正**：
1. 投影表结构中，每个"来自特定源"的字段加 `source_health` 字段，记录该源最后成功读取的时间、当前故障状态
2. 展示层必须标记"该字段数据源当前有故障"
3. 投影重建前输出"缺失清单"，列出因故障而未投影的事实数、来源与影响的任务数
4. 故障恢复后，显式对账"已恢复 N 条"，而非静默更新

**一期还是后置**：一期规则与展示（实现后置）。

## 应从 MVP 删掉的 3 项

1. **跨源自动关联与模型补盲**（从第 1–2 阶段删掉）
   - 理由：C1、C2、C5 暴露出身份模型与合并规则都不成熟，早期关联会污染数据，修复成本更高。应先保证单源的证据流水线准确，再考虑跨源聚合。
   - 替代方案：用户可在 CLI 手工指定 `task link <task_id> <evidence_id>`，逐件确认。

2. **Cursor 支持与完整性承诺**（从第 1–3 阶段删掉）
   - 理由：C3 与 C8 表明加密与 IDE 覆盖缺口无法在早期闭合，标记 partial 会误导用户。不如首期 unsupported，等 spike 完成再决定支持范围。
   - 替代方案：DSH + Codex + Claude + OpenCode 足以覆盖多数工作流。

3. **自动状态推进与隐含验收条件推导**（从第 1 阶段规则中删掉）
   - 理由：C4 表明无验收条件时的推进会被滥用，而验收条件推导又容易出错。应强制显式定义，保证早期投影的权威性。
   - 替代方案：状态停留在"进行中"，由用户或权威系统显式推进至"待验收"。

## 设计未回答的 3 个问题

1. **当同一实体（如一个 PR）在多个来源有记录时（GitHub 原始记录 + DSH 会话引用 + Codex 工具输出），如何去重而不误合并？**
   - 设计说"保留来源身份，再按已验证规则折叠"，但未给出"已验证规则"的具体清单或优先级。
   - 当前假设：GitHub PR 是权威，其他是引用。但若 Codex 的 PR 数据比 GitHub 更新（例如后续提交），该相信哪个？

2. **投影与日志的不一致如何检测与报告？**
   - 设计提到"投影失败从日志补齐"，但在运行中，两者何时同步、何时允许不一致、何时强制校对都未定义。
   - 用户运行 `harness-registry integrity-check` 时，应输出什么级别的警告才能让用户采取行动？

3. **与存量系统的拉取式集成如何处理权威冲突？**
   - 设计说"若 taskboard 与 PTC 对同字段都声称权威，阻断并请用户裁决"，但没有说如何让用户快速做出这个裁决。是在 CLI 中、还是在 DSH 中、还是需要全新的 UI？
   - 首期是否支持 taskboard / PTC 的拉取，还是只能手工配置别名？

## 如果只能保留一个来源

**选择：DSH**

**理由：**
- DSH 的数据模型最清晰（消息、工具、todo、ticket），格式最稳定（zstd 压缩已验证）
- 包含最多跨 Agent 的显式锚点（worker、ticket_id），减少后期猜测的空间
- 本机 1,424 个会话足够建立 200+ 标注片段、50+ 任务的验收集，达到 MVP 门槛
- Claude、Codex、Cursor、OpenCode 的各类缺陷（加密、压缩变化、归档不完整、并发难预测）都会在多源聚合时放大；单源则风险可控

**削减的结果**：
- 无法自动聚合 Cursor IDE 工作与其他 Agent 的代码审查（但可用 PR 作手工锚点）
- OpenCode 的 todo 丢失（但 DSH 的 todo 足够补偿）
- Claude 的结构化任务不可见（但会话摘要可补偿）

**恢复路线**：第 2 阶段加 Codex（归档完整性已验证），第 3 阶段加 Claude（子代理去重已验证）；Cursor 与 OpenCode 推后到第 4 阶段或更后。

## 对主控约束的反挑战（如有）

### 反挑战 1：约束 3"进度不得伪精确"与设计的"七类条目计数"冲突

**设计说**：投影输出"已验收条目 / 明确验收条目"计数，不输出百分比。
**但约束说**：没有验收标准就不给百分比。
**问题**：假设任务有 5 个 goal，其中 3 个已验收、2 个未验收。输出"3 / 5"满足约束吗？还是这个计数本身就是"伪精确"（因为没有说是否等权重、是否相互依赖）？

**建议澄清**：计数输出时必须明确说"N 条已验收的目标，其中…(无序列表)"，而非数字比例。

### 反挑战 2：约束 5"每条事实要有来源会话与事件"与"跨 Agent 任务"冲突

**约束要求**：证据可回链，必须指向具体会话与事件。
**现实**：当任务跨 DSH 和 Cursor 时，合并后的事实无法回链到单一会话；或要么记为"来自多个会话"，要么拆分为子事实。

**建议澄清**：是否允许 `evidence_ref` 包含数组（多会话），还是必须拆分？若拆分，如何在投影中展示"这三个拆分事实其实来自同一个用户行为"？

### 反挑战 3：约束 6"只读聚合"与"登记权威"的定义不一致

**约束说**：登记表不得双写 taskboard / PTC。
**设计说**：登记表对"未进入上游的任务"有权威。
**问题**：如何定义"进入上游"？是"手工映射过"还是"自动检测过"？若新增来源导致现有任务被重新分类为"未映射"，是否失去登记表的权威性？

**建议澄清**：引入 `task_provenance` 字段，明确记录"此任务由 taskboard 读取（权威在上游）"vs"此任务生成于登记表（权威在本地）"，不能动态切换。

## 最可能失败的原因（3 个，按概率排序）

### 1. 任务误合并导致历史污染（概率 65%）

**信号**：
- 第 1–2 周内，自动关联率 >5% 但人工否决率 >30%（说明规则精度低）
- 已验收任务后来被拆分为两个独立任务（说明早期合并有误）
- 投影中出现"冲突"记录数与"关联"记录数比例 >1:10

**止损动作**：
- 立即冻结自动关联功能，改为候选建议
- 对前 100 个自动合并逐一人工复核，统计误合并率
- 若误合并率 >5%，回溯所有投影，拆分已验收的误合并任务；不能简单标记冲突，必须恢复独立历史

---

### 2. 源格式变化或故障导致增量停滞（概率 55%）

**信号**：
- DSH zstd 帧边界检测失败，导致某个会话后续增量无法读取（实测中已知多帧情况）
- Codex 归档文件格式变化，导致投影游标跳跃或重复
- OpenCode 时间戳不单调，导致消息重复或丢失，修复需要人工审计

**止损动作**：
- 实现每日"投影完整性检查"，输出"上次成功读取距今 > 4 小时"的预警
- 对每个来源设置"最大积压事件数"阈值（例如 >1000 未投影），超过时停止新增，改为报告"需人工审计"
- 准备"投影重建"脚本，支持从任意检查点恢复，不依赖线性续读

---

### 3. 与存量系统的边界模糊导致权威冲突升级（概率 48%）

**信号**：
- 登记表与 taskboard 对同一任务的状态出现分歧（例如登记表"待验收"vs taskboard"进行中"）
- 用户询问"这个任务到底完成了吗"时，两个系统给出不同答案
- 后期试图开启写回功能时，发现幂等接口无法定义（两个系统对"完成"的定义不同）

**止损动作**：
- 第 0 阶段必须产出"权威矩阵"与"边界案例 10 个"文档，获得用户与相关系统所有者的签字确认
- 第 1 阶段投影中，每个"状态"字段必须分离为 `登记表推荐状态 / 权威系统状态 / 冲突标记`，不能合并显示
- 若冲突超过 10%，立即降级为"只读展示"模式，冻结自动推进，要求用户全部手工确认
