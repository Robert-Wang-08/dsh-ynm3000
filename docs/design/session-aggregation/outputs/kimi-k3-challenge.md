# Kimi K3 独立挑战：多 Agent 会话聚合与统一任务登记

## 结论（≤150 字）

架构方向（账本先行、只读投影、锚点优先）可落地，但设计稿在四个实测点上站不住：首建模型回填与每日预算矛盾，会产生上千条人工队列；Node v24 内置 zstd 解不了多帧 DSH 文件，增量路径依赖未打包的外部 CLI；OpenCode 1.9GB 活库的读法会顶 WAL、拖慢写入方；"98% 精确率"用 200 段样本在统计上刚好踩线、无对抗集。一期只做 DSH 事件账本，其余全砍。

## 挑战清单（C1..C10）

**C1 首建体量与预算自相矛盾**
- **严重度**：高
- **主张**：设计既设每日 200 次调用/100 万 token 上限，又要求历史回填，二者在真实体量下冲突。
- **反例/实测风险**：1,424 个 DSH 会话按保守每会话 3–10 段得 5K–14K 段，弱锚点按 30–40% 计约 2K–5K 次模型调用、8M–20M 输入 token。在每日上限下回填需 8–20 天，且 0.75–0.98 置信带若占 20%，首日即产生 1,000+ 条人工确认队列。OpenCode 还有 43,028 个 part、218 条 todo 未计入。用户第一天看到四位数待办队列即流失。
- **最小修正**：历史回填一律不进人工队列，弱匹配只落 `related` 建议并折叠；人工队列只收"首建之后"的增量；`review_queue` 加 `origin=backfill|incremental` 字段。
- **一期还是后置**：一期必须改。

**C2 DSH 多帧 zstd 依赖未声明的外部运行时**
- **严重度**：高
- **主张**：增量解析器建立在"逐帧迭代"上，但本机 Node v24 内置 API 只解首帧，设计未指定帧迭代实现与依赖打包。
- **反例/实测风险**：实测 689,420 字节只解出 276 字节首帧——若实现者随手用 `zlib.unzipSync`，将静默只读到每个会话第一条记录，1,424 个会话全部变 partial 且无任何报错。调 zstd CLI 则引入 Windows 下 1,424 次子进程（每次 30–80ms）、PATH 依赖、杀软拦截。DSH compaction 重写前缀时 seq 是否延续未验证；若 seq 归零而 event_id 由 seq 派生，直接撞旧事件。
- **最小修正**：阶段 0 spike 锁定帧迭代库（如 zstd-napi 或内置 stream 手动帧循环）并写进依赖清单；event_id 必须含 `generation`；解析器对"解出记录数=1 但文件>10KB"做硬告警。
- **一期还是后置**：一期。

**C3 OpenCode 活库读取会顶 WAL、拖写入方**
- **严重度**：高
- **主张**："只读短事务"在 1.83GB DB + 79MB WAL 且 OpenCode 正在写入时不成立。
- **反例/实测风险**：对 `part` 表做首批 43,028 行的 JSON 抽取是秒级到分钟级事务；读事务存活期间 WAL 不能 checkpoint，79MB 会继续膨胀，写入方延迟上升。用 `immutable=1` 打开则整个 WAL 不可见，丢掉最近全部增量；只复制主库文件不复制 `-wal/-shm` 同样丢。Windows 上复制 1.9GB 快照还会触发 Defender 实时扫描，耗时 10–60 秒且占满磁盘。
- **最小修正**：增量路径直接以 `mode=ro` 打开活库、查询限时 15 秒（与既有预算一致）、显式 `PRAGMA query_only`；首建用 SQLite backup API 在线备份到临时副本；把"WAL 大小"纳入仪表盘 lag 指标。
- **一期还是后置**：一期改读取契约，快照首建可后置到阶段 2。

**C4 增量水位在时钟与重写下有静默漏读路径**
- **严重度**：中
- **主张**：三类水位各有未覆盖的漏读场景，设计只给了重叠窗口一个方向性安慰。
- **反例/实测风险**：① OpenCode `time_updated`：若行在事务内带旧时间戳提交（批量导入、时钟回拨），10 分钟重叠不够；`todo` 表实测无独立 id，重叠去重键是什么未定义。② Codex/Claude JSONL offset：文件被压缩工具或 sync 软件重写时 offset 落在垃圾字节上，设计只说"generation 重扫"但没给 offset 处的校验手段。③ DSH 整文件解压 + seq 水位在 compaction 未验证前，"前缀哈希变化→重扫"会把 1,424 文件反复全量重解，30% 回填预算被打爆。
- **最小修正**：最小验证方法——各源各做一条注入测试：OpenCode 人为 `UPDATE time_updated = time_updated - 3600` 后跑增量断言不丢；JSONL 在 offset 处先读一行验证 JSON 可解析且 `native_event_id` 连续，否则回退 generation 重扫；DSH 记录每文件"重扫次数"指标，>2 次/周即告警。
- **一期还是后置**：一期（验证方法），分区审计后置。

**C5 Windows 运维假设过轻**
- **严重度**：中
- **主张**：计划任务 + 单写者锁 + 插件在真实 Windows 上有五个具体坑，设计一个都没回应。
- **反例/实测风险**：① 计划任务"未登录运行"需存凭据，且 `C:\Users\wwm_1\...` 用户 profile 在未登录时不可用，任务会静默失败。② 锁文件在进程崩溃后残留，Windows 无 flock 语义，需 OS named mutex 或 PID 活性检查，否则双调度。③ Cursor `AppData/Roaming/Cursor/User/workspaceStorage/*` 深路径可超 260 字符，无 `\\?\` 前缀和 longPathAware manifest 会 ENOENT。④ 本地服务若开端口，企业机防火墙弹窗；建议 named pipe。⑤ 项目路径含中文（如 `D:\src\ynm3000` 之外的客户目录）时 zstd CLI 参数编码在 GBK 控制台下出错。
- **最小修正**：部署章节增加 Windows 清单：named mutex、登录触发器、长路径前缀、named pipe、全路径 UTF-8 传递；阶段 1 验收加"崩溃后遗留锁可自愈"用例。
- **一期还是后置**：一期。

**C6 成本"便宜"结论缺首建实测，止损阈值过粗**
- **严重度**：中
- **主张**：8 万 token/日的示例只覆盖稳态，首建与重度使用两个尾部未定价。
- **反例/实测风险**：首建 8M–20M 输入 token（C1），按中高端模型 $3/M 为 $25–60，可接受；但若用户日并行 5+ 个 agent、日增 2 万事件、模型占比 30%，需 600 次/日，超上限 3 倍，队列单调增长，"积压超过 10,000 暂停摘要"成为常态，登记表永远不全。止损只有"排队"，没有"降级到纯规则模式"的明确开关。
- **最小修正**：成本章节加两条硬规则：模型调用连续 3 天超上限→自动切规则-only 并弹通知；首建前用 50 个会话采样实测真实事件率与弱锚点占比，再定预算，把数字写进裁决日志。
- **一期还是后置**：一期。

**C7 隐私三条可同时成立，但默认呈现会误导**
- **严重度**：中
- **主张**："本地抽取、脱敏外发、只存指针"技术上兼容，真正的问题在默认设置与用户感知。
- **反例/实测风险**：① 第八章默认每日 200 次模型调用，第十三章才说外发默认禁用——模型跑在哪？本机无 GPU 证据，CPU 跑 4K token 推理以分钟计，5 分钟可见 SLA 直接破产。② 凭据检测不是零风险：base64 包裹的 key、客户内部 token、中文语境私聊均可能漏检，而 UI 若显示"已脱敏"徽章，用户会误以为外发安全。③ FTS 索引"获准摘要"仍含人名/客户名；审计留存请求摘要的 digest 对短秘密是离线爆破 oracle。
- **最小修正**：把"模型运行位置"列为阶段 0 必答裁决；UI 文案从"已脱敏"改为"已检测，非保证"；审计只存模型目的地+策略版本+条目计数，不存 digest。
- **一期还是后置**：一期（文案与裁决），本地模型选型后置。

**C8 评测集在统计上撑不住声明的门槛**
- **严重度**：高
- **主张**：200 段/50 任务证明不了 98% 精确率与 80% 召回，且无泄漏防护。
- **反例/实测风险**：按 rule-of-three，200 次试验零错误仅支持下限 98.5%，贴线无余量；50 任务上 80% 召回的 95% 置信区间约 ±11%。"零误合并"在 50 任务上几乎无信息量——需要对抗集：同仓库不同目标、同客户不同任务、同 PR 服务两任务。同源同机的金标集有强自相似偏置；若标注时用过同一模型的输出做辅助，缓存键含内容摘要，评测即泄漏。
- **最小修正**：金标按时间切分（标注只用 11 月前会话，评测用之后）；至少 100 对硬负例；报告除 P/R 外必须含：锚点覆盖率（无硬锚点段占比）、人工队列负担（条/日）、回放三次事实数差异、证据可定位率。锚点覆盖率若 <30%，98% 精确率的意义要打折写明。
- **一期还是后置**：一期改造，对抗集可延到阶段 2 晋级前。

**C9 失败恢复清单缺"源删除后证据断链"与"解析器版本混布"**
- **严重度**：中
- **主张**：崩溃恢复（尾批次忽略、投影重建）想得细，但两个更常见的场景没答案。
- **反例/实测风险**：① 用户清理 `~/.dsh/sessions` 或 Codex 归档被删，墓碑有了，但任务卡里 100% 证据可回链的承诺破功——`evidence_ref` 指向不存在的资源，UI 是显示"证据已失"还是静默隐藏？② 插件/解析器升级后 cursor 带旧 `parser_version`，旧事件不重解析则同一投影混布两版语义，重解析则首建成本重演；设计未给重解析触发策略。③ quarantine 目录若只进不出且无仪表盘计数，就是静默丢数据的变体。
- **最小修正**：`evidence` 表加 `source_available` 状态位，断链证据在 UI 显式标灰；解析器升级默认只对新事件生效，重解析需显式命令并报告差异数；quarantine 计数进仪表盘必填项。
- **一期还是后置**：一期。

**C10 用户工作流没有入口理由，登记表是第五个孤立视图**
- **严重度**：高
- **主张**：用户已有 taskboard、dashboard、focus-hub、PTC 四个入口，登记表若不嵌入现有动线就是第五天被放弃的工具。
- **反例/实测风险**：设计让 DSH 插件"只做展示与提交确认"——这是对的方向，但验收标准里没有一条测"用户在既有界面看到登记表信息"，全部验收都在 CLI 与投影层。review 队列若按 C1 估算首日千条、日常每日 20–50 条，用户处理速率若为 10 条/日，队列单调发散；队列发散→任务卡停留在"待确认"→卡片不可信→不再打开。
- **最小修正**：阶段 1 验收加一条行为标准："taskboard/dashboard 至少一处展示登记投影字段"；review 队列设上限（如 200 条），溢出自动降级为 related 建议而非继续堆积。
- **一期还是后置**：一期。

## 应从 MVP 删掉的 3 项

1. **自动关联评分与置信带**：锚点覆盖率未实测前，0.75–0.98 带只会制造队列。一期只保留硬锚点自动关联 + 其余一律 related 建议。
2. **Codex/Claude/OpenCode/Cursor 四个适配器**：Cursor 根 blob 未解密、Claude 子代理去重未验证、Codex 归档完整性未核对——四个源各带一个未验证炸弹，五源齐上故障面是 DSH 的五倍而边际价值递减。
3. **七类任务卡的完整版**：`insights/plan/decisions` 三类无锚点可依附，一期只会靠模型硬编，污染账本。一期卡片只保留 goals/artifacts/todos 三个有结构化痕迹（todo/write、session/title、ticket_id）支撑的字段。

## 设计未回答的 3 个问题

1. **task_id 的跨重建稳定性**：稳定 ID 本地生成、重建靠纠正日志——日志部分损坏或换机迁移时 task_id 是否漂移？外部系统（taskboard）若引用了旧 ID，谁来维护重定向表？
2. **OpenCode `todo` 无独立 id 的去重键**：218 条 todo 在重叠窗口里靠什么判重——`session_id+content+position` 哈希？content 被编辑后是同一 todo 还是新 todo？这直接决定待办字段的准确率。
3. **模型运行位置与 5 分钟 SLA 的优先级**：外发默认禁用、本机无 GPU 证据，则"自动关联"实际是"数小时后出现"。设计必须明说：5 分钟可见的只是证据层，任务层是异步且可能隔天的——否则用户预期从第一天就错位。

## 用户会在第几天放弃，为什么

第 3–5 天。第一天首建跑完，打开看到：DSH 之外的源全是"partial/未验证"标签（设计自己的诚实标注在此时是负资产），加上按 C1 估算的数百至上千条 review 队列。用户处理 20 条后发现队列不见底，且任务卡里"待确认"占多数、进度栏全是"无验收条件不计百分比"——信息密度低于他已有的 taskboard。第三天起不再打开；第五天计划任务照常扫描、队列继续涨，工具沦为后台噪音。根因不是解析失败，而是**把确认成本一次性摊给了还没建立信任的用户**。

## 对主控约束的反挑战

1. **约束 2（身份优先于语义）与约束 9（每阶段可验收）存在实测张力**：盘点第 4.5 条已确认跨源无全局 ID，硬锚点在跨源场景天然稀缺。若严格执行约束 2，阶段 2 的"自动关联精确率≥98%"验收将只覆盖占比可能不足三成的有锚点段，验收通过但用户感知的自动覆盖率很低。建议主控补一条：验收报告必须同时给出锚点覆盖率，精确率门槛只在有锚点子集上生效，避免"达标但没用"。
2. **约束 5（证据必须可回链）需加降级条款**：源文件被用户清理是常态而非异常，绝对化的"无来源事实不得入库"在源删除后会使已入库事实陷入"来源已失"的灰色态。建议改为"入库时必须可回链；来源消失后保留事实并显式标记证据失效"，否则 100% 覆盖率的承诺必然在某次清理后破功。
