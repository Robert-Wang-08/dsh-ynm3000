# 任务：以 Opus 5 角色独立挑战「多 Agent 会话自动聚合与统一任务登记」设计

你是独立架构挑战者。只审查，不写代码、不改文件、不替设计者辩护。目标是找出会让这个设计在真实使用中失败的结构性缺陷，而不是润色文字。

## 输入

1. 6astra 主设计稿（下文）。
2. 本机实测盘点（下文）。
3. 主控约束（下文）。

## 主控约束（挑战时以此为准，不要另立教条）

1. 会话不是任务：同一会话可含多任务，同一任务可跨会话/跨 Agent；任务必须有稳定 ID。
2. 身份优先于语义：只有外部任务号/PR/commit/native task 等硬锚点可自动合并；语义相似只作候选。
3. 进度不得伪精确：没有验收标准就不给百分比；不用消息数/工具数冒充完成度。
4. 自报不销项：助手说“完成”、子代理退出 0、测试通过，都不能单独把任务标 done。
5. 证据必须可回链：每条事实要有来源会话与事件；无来源事实不得入库。
6. 只读聚合：登记表不得双写 taskboard/PTC/superagent；同一事实只能有一个写权威。
7. 增量必须贴合真实格式：DSH 是整文件 zstd、OpenCode 是 1.8GB SQLite+WAL、Cursor 根 blob 加密；不要假设存在逐事件流。
8. 不扩成系统：第一期不做向量库、不做常驻大 Agent、不做自动写回、不做多租户。
9. 每阶段可验收：给可测试的通过标准；不要“大爆炸上线”。
10. 未验证项必须标注：Cursor 解密、DSH compaction、Claude 子代理去重、Codex 归档完整性都还没有定论。

## 你必须回答的问题

1. **身份模型**：任务/段/证据三层是否足够？一个会话多任务、一个任务多 Agent、同一任务在两个 Agent 各做一半，这三种情况各会怎么错？给出反例。
2. **合并规则**：A0/A1 自动、A2 快速审查、A3/A4 只候选，是否会被“同名不同项目/同 PR 不同目标/跨 Agent 重复劳动”击穿？最小修正是什么？
3. **账本与投影**：append-only JSONL + SQLite 投影 + Markdown 卡片，是否过度设计或不足？崩溃、并发、重建、迁移各有什么缺口？
4. **验收与进度**：证据等级和自动边界是否能阻止“假完成”？找一个具体反例，说明现在的规则会怎么放过它。
5. **适配器契约**：面对加密、压缩、归档、并发写、schema 漂移，契约缺什么？Cursor 只接 transcript 是否诚实？OpenCode 的 1.8GB 读取是否可行？
6. **与存量系统**：登记表声称“只读投影 + 未进入上游任务的登记权威”，这个边界是否自相矛盾？会不会事实上变成第二任务系统？
7. **MVP**：P0/P1 的验收是否真的可测？如果只能保留一个来源，选哪个、为什么？应从 MVP 删掉哪三项？
8. **隐私/注入**：会话内容是不可信数据；抽取模型无工具、只输出 JSON、引文回链，是否足够？还缺什么？
9. **可运维性**：一个普通用户能否安装、排障、恢复？失败时会不会静默丢数据？
10. **最可能失败的原因**：给出 3 个，按概率排序；每个给一个早期信号和止损动作。
