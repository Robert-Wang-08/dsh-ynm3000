# dsh web 两次卡死：根因分析（2026-10-20）

> 结论先行：**不是 DSH 里的 JS 死循环，而是整机内存超配引发的交换风暴（thrashing）把宿主进程饿死。**
> 触发点是 PTC 批量派发；火绒 + 腾讯电脑管家的实时文件防护、C: 盘只剩 23.7 GB、libuv 只有 4 个线程池线程，是三个放大器。

---

## 一、机器画像（决定了"为什么是这台机器上出事"）

| 项 | 实测值 | 来源 |
| --- | --- | --- |
| 逻辑处理器 | 16 | `[Environment]::ProcessorCount` |
| 物理内存 | **约 16 GB** | 提交上限 42.87 GiB − 页面文件 27 GiB |
| 页面文件 | **27 GB，在 D:** | `D:\pagefile.sys` |
| 提交上限 | 42.87 GiB | `\Memory\Commit Limit` |
| 当前提交量 | 18.7～19.4 GiB（故障后常态） | `\Memory\Committed Bytes` |
| 当前可用内存 | 2.9～4.0 GB | `\Memory\Available MBytes` |
| C: 剩余 | **23.7 GB / 约 463 GB（≈95% 满）** | `Get-PSDrive` |
| D: 剩余 | 143.3 GB | 同上 |
| 安全软件 | 火绒 `HipsDaemon` 运行中（`sysdiag.sys` 过滤驱动已加载）+ 腾讯电脑管家 `TFsFltX64_ev.sys` | 服务状态 + 启动日志 FilterManager |

**关键点**：系统在"什么都没干"的常态下，提交量已经是 18.7 GiB，而物理内存只有 16 GB —— 也就是说**平时就已经有 2~3 GB 在靠页面文件硬扛**，缓冲余量极薄。任何一次并发上升都会直接把系统推进交换。

## 二、触发点：PTC 批量派发

两个故障窗口前，都出现了密集的 PTC 派发。以第二次（14:19）为例，skillhub 会话 `3dd68e2c` 的 turn 159：

```
14:18:59  assistant/message
14:19:00  tool/ptc-dispatch-start ×2      ← 2 个 worker
14:19:13  tool/ptc-dispatch-start ×2      ← 累计 4
14:19:20  tool/ptc-dispatch-start ×1      ← 5
14:19:29  tool/ptc-dispatch-start ×1      ← 6
14:19:46  tool/ptc-dispatch-start ×1      ← 7
14:19:47  step/end → step/start           ← 之后 98.5 秒静默
14:21:31  turn/end {kind:"interrupted"}
```

**46 秒内 7 个 worker。** 每个 worker 走一条子代理路由：走 ACP 的那些是**外部 CLI 子进程**（web profile 里已配好 `cmd /c opencode acp`，另有 kimi/cursor/codex/claude 等同类路由），其余是宿主内子代理。这些 CLI 基本都是 Node 程序，单个数百 MB 量级，7 个并发就是 GB 级的新增常驻与瞬时映像扫描压力。

第一次（13:41–13:42）同样：`13:41:20 ×2 → 13:41:35 ×2 → 13:42:07 ×1`，5 个 worker，`turn 158` 在 13:42:08 被切断。

同期还有 4～5 个会话在活跃写盘（14:18–14:22 四个会话合计 516 条事件），其中 `3dd68e2c` 已跑 160 回合、日志 13.6 MB 压缩 / 41.5 MB 明文，`15c93605` 19.1 MB 压缩 / 61.6 MB 明文。

## 三、现场留下的痕迹（这是"饿死"最硬的证据）

把 `~/.dsh` 下所有文件在故障窗口的写入时间排出来：

```
13:43:42   storages/session_projcache/sessions/.d41e901a-….tmp   63,461 B   ← 只写了一半
            ……此后 24 分钟零写入（会话仍处于活跃回合）……
14:07:34   WindowsTerminal 注册表配置单元卸载  ← 你关掉了窗口
14:08:04   会话写入恢复（新实例）

14:22:09   最后一个会话日志写入
14:28:58   storages/session_projcache/sessions/.e7ea23b2-….tmp        0 B   ← 一个字节都没写进去
            ……此后零写入……
14:33:53   Application 日志：User Profiles Service「系统资源不足，无法完成请求的服务」
14:34:00   Kernel-Power 109：关机转换，原因 Kernel API（主动重启，非崩溃）
```

四条判据：

1. **全库只有这两个 `.tmp` 残留文件**，时间刚好落在两次故障的尾部 —— 不是日常杀进程的碎片，是"写盘写到一半被冻住"的墓碑。
2. **projcache 检查点的写入协议是**（源码 `dsh-storage-json`）：`open(tmp,'wx')` → `writeFile` → `fsync` → `rename` → `fsync(目录)`。留下 63 KB / 0 B 的 tmp，说明进程在 `writeFile`/`fsync` 阶段就再也没往前走。
3. **此后 20+ 分钟没有任何写入**，而当时有 4 个会话的回合是打开状态（`08abec00`、`5616c99f` 的回合到今天仍然悬空未闭合）。会话日志每次追加都要 fsync，如果主线程还在跑，不可能一条都不写。
4. **没有崩溃**：无 BugCheck、无 WER 报告、`CrashDumps` 里没有 node 的 dump。进程是"活着但不动"。

## 四、为什么表现成"Ctrl+C 退不掉"

这是同一个机制的三连锁：

1. 进程的响应依赖调度和内存页 —— 交换风暴下它拿不到 CPU 时间片，也频繁等缺页。
2. Node 的 `SIGINT` 处理要回到 event loop 主线程执行 —— 线程得不到调度，信号就永远"已收到、未处理"。
3. 就算处理了，DSH 的退出路径本身还要写盘（会话日志 append + fsync 检查点）—— 而写盘正是卡住的地方，于是优雅退出也退不出去。

所以"Ctrl+C 无效 + 页面转圈 + 进程还在"是**资源饥饿**的典型指纹，而不是"某个循环写错了"。

顺带解释另外两条现象：
- **刷新连不上**：服务端口还在监听，但每个响应都要读盘（静态资源、会话数据），线程池全堵 → 只能接受连接、永远不给内容 → 看起来像"连不上"。
- **为什么不会自己恢复**：7 个 ACP 子进程 + 大会话的工作集一直在 16 GB 之上，交换状态不会自行解除，只有杀掉进程（或重启）才能把工作集放下来。

## 五、代码与系统层的三个放大器（不是主因，但把"慢"放大成"死"）

| 放大器 | 实测/源码证据 | 影响 |
| --- | --- | --- |
| **libuv 线程池只有 4 个线程** | `UV_THREADPOOL_SIZE` 未设置（用户级/机器级都为空），16 核只有 4 个线程干磁盘活 | 所有 `fs`/`zstd`/`crypto` 异步操作排队；4 个线程被 fsync 占死，全进程就"什么都做不了" |
| **每次会话事件追加都 fsync** | `dsh-session-persistence-jsonl` 的 `appendLines` 路径 `await handle.sync()` | 事件写入与磁盘延迟强绑定；故障时正好卡在这一步 |
| **安全软件实时防护** | 火绒 `sysdiag` + 腾讯管家 `TFsFlt` 两个内核文件过滤驱动在链上；PTC 批量派发瞬间又是 7 个新可执行映像要扫描 | 每个 open/rename/fsync 都可能被同步扫描，是急性卡顿的常见来源 |
| **大日志的同步解码** | `zstdDecompressSync` 在主线程：最大的 19.1 MB 会话解一次 474 ms；全部 520 个会话 327.6 MB，裸解压 6607 ms | 任何"重扫会话"的动作都会把 UI 冻结数秒 |
| **ACP 适配器同步走树** | `workspaceSnapshot()`：`readdirSync` + 每文件 `statSync`，上限 2 万文件 | skillhub 工作区 3994 文件 = 每次 210～574 ms；每个 worker 起跑前、结束、每 30 s 探活各一次 |
| **C: 盘 95% 满** | 23.7 GB / 463 GB | NTFS 碎片与元数据压力，实时防护与页面文件都在同一物理盘上抢带宽 |

对照：**现在的 I/O 通路是健康的**（`open+write` p50 0.6 ms、`fsync` p50 1.1 ms / p99 5 ms / max 12.9 ms）。所以卡死不是慢性病，而是"急性事件"——只有在并发+内存压力同时到位时才发作。

## 六、结论与不确定性

**主因（高置信）**：PTC 批量派发（7 个子进程）叠加 4~5 个大会话，把 16 GB 物理内存顶穿，系统进入交换；宿主进程被饿死，进而写不动盘、退不出、页面连不上。

**次因/并发现象（中置信）**：写盘路径（fsync + 两个文件过滤驱动 + 4 线程池）在这段时间里成为不可用的瓶颈，这解释了为什么最后一条痕迹恰好是"半截的 projcache 写入"。

**未能直接证实的一点**：故障瞬间的 CPU 占用、内存读数、主线程是否有 JS 栈 —— 现场没留。两种机制（内存饥饿 vs I/O 卡死）在事后只能靠间接痕迹区分，下次卡死时用 `Capture-Hang.ps1`（尤其带 `--inspect` 时）可以一次定死：

| 下次观测 | 判定 |
| --- | --- |
| 探活无响应 + 主线程 evaluate 超时 + CPU 低 + 提交内存高 | 内存饥饿（本报告主因） |
| 探活无响应 + 主线程 evaluate **有**响应 + CPU 低 | I/O/线程池卡死（次因） |
| 探活无响应 + CPU 单核打满 + 热点函数集中在某插件 | JS 同步死循环（本次未支持此假设） |

## 七、处置建议（按性价比排序）

1. **PTC 派发限流**：一次不超过 3 个 worker，分批派发。直接掐掉触发点，成本为零。
2. **给安全软件加排除**：`%USERPROFILE%\.dsh`、`D:\src`、opencode/kimi/codex/claude 的 CLI 安装目录，避免每文件实时扫描。
3. **放大线程池**：设用户环境变量 `UV_THREADPOOL_SIZE=8`（16 核），让磁盘活不再挤在 4 个线程上；当前 4 个线程是默认值。
4. **DSH_HOME 迁到 D:**：C: 只剩 23.7 GB，会话+存储都在 C:；D: 还有 143 GB。迁移需走备份/恢复流程。
5. **大会话断代**：160 回合 / 61.6 MB 明文的那条已经偏大，按主题开新会话，或先归档。
6. **启动方式换成带 inspector 的包装**（`Start-DshWeb-Inspect.ps1`）+ 常驻 `Watch-DshWeb.ps1`，下次卡死自动留证。
